# Football analytics system
The objective is to create a system that pulls the available football data and creates a dataset ready to use in the pipeline of a model. The output of this feature engineering step should be the following set of artifacts: 
- Snapshots table: The snapshots table will hold all the computed columns, even if they will not form part of the final output. The purpose is to have an indexed and easy way to access the computed features, including all the columns that are specified as requirements of other templates. This table will also hold the ratings of the teams so they can be updated sequentially when another match comes. The final features that will form part of the output will be specified in a white list. The structure of the snapshots table will be given by:
    - Key: The canonical ordering for the snapshots table will be ["league", "season_start", "round", "match_order", "team_id"] regardless of the export mode. The long/wide format will be given later at a pivoting stage.
    - Columns: All lagged features, Glicko ($\mu$,$\varphi$,$\sigma$), flags (promoted, demoted, home , away, etc), and warm_start coefficients.

The workflow will be the following
0. Load the data to process. Through a GUI we will specify the feature and target templates for the feature engineering and design of the model.
1. This stage will be directed by an _orchestrator layer_ (a lightweight classer or a pipeline registry) to run passes in a strict temporal order. The output will be a list of artifacts that will be described later. There will be 4 passes:
    - Pass O: Receive a list of templates. The orchestrator should first scan the templates for >retrieve_location indicators and replace them with the information from the given location. Then, it should look at the families, output names, and requirements fields of all the templates in order to build a DAG (Directed Acyclic Graph) that represents the order in which the features should be computed.  The main temporal order is league-wide pass -> team-wide pass -> ratings pass. Furthermore, for features called inside "requirements" fields, the orchestrator first should look within the list of column output names if the feature is already computed (in which case it is reused), and if it is not present, then the orchestrator needs to run those templates before the one calling them.
    - Pass A: League-wide pass. 

## Creation of feature templates
The idea is to have three ingredients:
- A library of _operators_ and _operator building blocks_ that act on the given data and have their own available configuration. These operators could be built or enhanced using the _operator building blocks_ as specified by _templates_ that include all the details about the operators. The details of these templates will be given below. The idea is to have a dynamic library that we can actively update by adding any new element to a corresponding registry. There will be kernel registries, aggregation registries, partition registries, etc.
- A list of _templates_ which specify features that can be obtained from data. Those templates have a given name and indicate the way in which _existing operators_ should be
used and with which configuration in order to obtain the desired/required features. At the same time, each operator will expose metadata so our _auditor_ can make sure that the operator being used in a template supports the options that we are asking for in the template.
- An _interface_ (i.e. GUI) that allows to choose _existing templates_ and specify the values of the blank/multiple choice fields or create new templates from scratch (with a predefined structure).

After specifying the set of templates that will be used for feature engineering, the _orchestrator_ will decide the DAG of the tasks required for computation and output some artifacts containing the engineered features and the run metadata. The library of choice for the computation of all the features is Pandas. First we explain the format convention for the templates for both features and targets. Once the conventions are established, we will specify how the templates will be used in the passes through the _orchestrator_ and _auditor_. Finally, we will describe what the output artifacts will be.

## Standard design for templates and artifacts
The format of choice for the design of the templates is the JSON format. The fields that contain the >parseable< string, will require the user to specify the relevant input when a specific template is chosen in the UI. The >parseable< indicator will always follow the key of the field it belongs in, so if for example we have "weeks_back": >parseable<, this means that the UI needs to show us the text "weeks_back" when asking for user input. After input, the >parseable< indicator is replaced by whatever the user input was. For fields that contain the >selection< string, the UI  will offer a selection of options to the user, and the user will select the desired ones by using checkboxes. Since >selection< fields will accept lists, when several checkboxes are selected for the same field, then it just means that a list will several elements will be passed. For the fields that contain strings se parated by the | character, the UI will ask the user to choose the desired setting, and then will overwrite the field with the user's choice, for example "league" | "team" will become "team" after the user chooses "team" in the UI. The fields that have the >retrieve_location string will have their information obtained from the relevant field of the template as indicated by the "location", for example >retrieve_parameters_window will retrieve the window length where the parameters field contains a dictionary {"window": 15}, in this example it will retrieve the number 15. The retrieval step is performed by the orchestrator once the parsing and selection fields have been filled for all the selected templates. 

### Feature template
- name: A string that indicates the name of the feature. Naming format is capitalizing the first letter of each word, with no spaces. Some examples are "RollingMean", "ExponentialMean", "StatRatioDifference", etc.
- family: This field will contain a string that indicates on which feature family a particular operator will operate. The purpose is that this, together with the warm-start status will determine the partition over which the operators will act. The supported families are "league" | "team" | "rating" | "headtohead" | "postprocessing". "postprocessing" is used for example for shrinkage or warm-start operators. Which family is picked when specifying a template will be indicated by the choice in the GUI. 
- kernel: This string will indicate  which aggregation kind a particular operator will use. The list is "rolling" |"expanding" |"snapshot" |"point" |"expression" | "teacher". Here the "expression" type is reserved for custom features that we will implement using a _feature builder_ and will have custom aggregation rules, and "teacher" will be reserved by those features that will be given by the output of pretrained models.
- parameters: Any parameters needed to specify the set up of an operator, can be a dictionary {"param_1": >parseable<,...,"param_k": >parseable<}. For example {"window":>parseable<, "smoothing":>parseable<} where "window" is used for "rolling" kernels and is just to specify the length of the lookback, and "smoothing" could be an additional smoothing done on the data.
- partition: Several types of partitions depending on the family and warm-start status. The indicate how Pandas vectorizes the computations. Some of the options are for league and no warm-start: ["league"], league and warm-start: ["league","season_start"], team and no warm-start: ["team_id"], team and warm-start: ["team_id","season_start"], head to head and no warm-start: ["team_id","opponent_id"], head to head and warm-start: ["team_id","opponent_id","season_start"]. More could be added at a later point. Usually some choices will be specified in the template, but it will be the job of the operator logic to select one depending on the warm_start choice of the user.
- inputs: Specifies on which of the column or columns of our data dataframe the operator acts on. The arguments of the features are indicated by keyword arguments and we need to specify which feature should be fed into each argument. If a list is given, the meaning is that the feature should be applied individually to each column and yield an output columns for each element in the list. For single variable features, we consistently will use "x" for the keyword argument, for example: {"keyword": "x", "args": >selection<}. If for example, {"keyword": "x", "args": ["team_45_min_Goals","team_45_min_Cornerkicks"]} is given, where there are two elements of the list, the meaning is that we apply the feature to each column and each application yields its respective output. For multivariate features, we use a similar convention: [{"keyword": "x", "args": ["team_45_min_Goals","team_45_min_Cornerkicks"]}, {"keyword": "y", "args": ["opponent_45_min_Goals","opponent_45_min_Cornerkicks"]}]. This means that the bivariate feature in question takes two keyword arguments "x" and "y", and it will act on two pairs ("team_45_min_Goals", "opponent_45_min_Goals") and ("team_45_min_Cornerkicks", "opponent_45_min_Cornerkicks"), and yielding one output column per pair. Notice that the pairs are taken with the respective order they appear on each list. The convention for the input column names will in general be prefix_stat, where:
    - prefix could be "team", "opponent"
    - stat is the name of the stat in question, some examples are "Standing", "BallPossession", "Cornerkicks", etc. Most stats will have an additional "half" segment appended half_stat, where  half could be "45_min", "90_min", or "total", for example opponent_45_min_Goalkeepersaves. In this case the "stat" part is 45_min_Goalkeepersaves. The "half" part could also be absent, like home_standing. There is no real issue here as long as we keep the UI aware of this when writing down the input names on a template.
For templates called from the requirements of other templates, the orchestrator will pass directly the dictionaries in the format required by the "inputs" field, so that no selection is needed.
- aggregation: This string specifies which is the operation performed on the data and could be any available aggregation method we have in our library. Some examples are "sum", "count","mean","var","std","rate", "custom" (in the case of teacher modules that have their own aggregation), or for the case  of "expression" kernels, we will have the aggregation indicated by full expression _Abstract Syntax Trees_, as will be described later.
- output: This is a string indicating the name of the output column. The naming convention will be prefix_stat_(parameters)feature, where:
    - prefix is as in the input
    - stat is as in the input
    - (parameters) is a string listing the value of the parameters used in the configuration of the feature. For example, for a RollingMean with lookback of 15, (parameters) is 15. Since "params" is specified as a dictionary listing the parameters, if there are multiple parameters, then (parameters) is just the collection of the values, like (15,20,8) where parameters is {"param1": 15,"param2": 20, "param3": 8}
    - feature is the name of the feature (the "name" field of this template), e.g. "RollingMean", "ExponentialMean", etc.
- requires: Requirements for the current feature. The idea is that if they are not necessarily kept for the final output, but they may be added to a _snapshots_ table in case they are necessary for some intermediate calculation. The format for the requirements would be for example for a rolling zscore standardized with league priors: [{"keyword": mu, "feature": RollingMean, "family": league, "parameters":>retrieve_parameters_window}, {"keyword": sigma, "feature": RollingStd, "family": league, "parameters":>retrieve_parameters_window}]. The keyword will correspond to the keyword arguments that the feature receives in the input. For the zscore, the formula is (x-mu)/sigma, where x is the input stat. This way, when asking for requirements, we know as what argument each requirement is supposed to be passed as. We can optionally add an "args" key to the dictionary representing each requirement, where if given, the required featured will be computed on that specific stat, while if not given, it will default to the same input as the original feature (in this case the feature on which the zscore is computed on). We also pass the parameters for the configuration of the requirement features as a >retrieve field, so that the orchestrator can complete them by looking at the configuration of the main template. By knowing all this information, the orchestrator can put together the final output name that the required columns will have and compare it to the output names from all the other templates when deciding how to build the DAG.
- is_loo: Stands for "is leave-one-out". This will be a Bool True or False that is True if the template describes a leave-one-out feature and False if not.
- shift_policy: Indicates the amount of shift the feature will have. The idea is to prevent information leak from the future or to give information to the model from a more distant past. The values would be either "nolag" for 0 lag or 1,2,3,..., depending on how many steps the feature is delayed.
- warm_start_blend: This will indicate the type of warm-start or shrinkage (if any) that a feature will use for borrowing strength from previous data or data from other teams. The structure is for example {"type": "LinearWarmStart", alpha_schedule: {"start_round": 1, "end_round": 6}}. The warm-start or shrinkage operators will be defined as features from templates that belong to the postprocessing family and their output will be a column with the weights corresponding to each round and also the column with the warm-started or shrunk features.
- audit: This is for ensuring congruence between the input, the settings, and the feature in use. One example could be {"min_count": 3, "allow_zero_var": False}.

### Target template
- name: A string that indicates the name of the target. Naming format is capitalizing the first letter of each word, with no spaces. Some examples are "BettingOption", "Winner", "Rank", "SingleStat" "MultiStat", "MatchTotal", "MultiTotals", etc.
- family: This string will indicate to which target family a particular operator belongs to. This will determine the partition over which the operators will act. The supported families for the targets are "team" | "match" | "bets" | "odds" | "rank". 
    - "team" targets is for example for a specific stat or group of stats for a single team in a match
    - "match" targets is for the pooled stats from both teams in a single match, for example total_corners = home_corners + away_corners
    - "bets" targets are for selecting suitable bet options for a particular match. They are meant to be used in classification problems where some examples are "more than 1.5 goals", "more than 2.5 goals", "less than 2.5 goals", etc
    - "odds" targets are meant to build our own set of odds as if we were bookmakers. Could be used paired with logit models.
    - "rank" targets are meant to be used to find the positions of the teams relative to each other and for finding tournament winners.
- input: Works the same way as the input for the feature templates.
- scaling: Indicates the desired scaler, some examples are "None", "league_zscore", "league_minmax", "team_zscore", "team_minmax", "quantiles", etc. Scalers will be defined as operators in our library, however, they will be able to check if the output columns already exist to avoid computing them again. For example, if we are already computing the league-wide z-score of a specific stat, then we should already have the league-wide mean and standard deviation computed, so we could reuse those columns for the scaler.
- scaler_partition: It is just the partition for the scaler. In case warm-start is used, we do not warm-start the targets, only the moments or any prior used in the scaler. For example, for a z_score scaler, only the mean and std for the scaler are warm-started, not the target stat.
- scaler_window: Specifies the lookback, we align it with the windows form the feature engineering.
- scaler_shift: Indicates the amount of shift that the scaler will have. In the same way as the targets, this allows to avoid peeking into the future. The values would be either "nolag" for 0 lag (for debugging purposes) or 1.
- transform: Optional operation on the raw target prior to scaling. Given by some operator in our library. Default is None.
- export_mode: "stacked" or "match_wide" depending if we export in long or wide format.
- audit: Same as before, it is for assuring consistency between targets and operators. Some examples could be a fallback to the unscaled target or using a global prior if variance collapses in early rounds {"min_std", "fallback": "use_mean_only"}

### Implementing a feature builder

For implementing a _feature builder_ we will work with the "expression" kernel introduced before. The idea of this type of feature is that the aggregation will be specified by Abstract Syntax Trees (AST) where the operations will be taken from our library of operators. One example of such feature is a difference of the ratios of the rolling means of the stat of one team against the other: Diff(Ratio(RollingMean,RollingMean),Ratio(RollingMean,RollingMean))

- inputs: In this field we list all the raw stats needed to build the expression. In our example ["team_corners_infavor","team_corners_against","opponent_corners_infavor","opponent_corners_against"]. In this case, when using the GUI to build a feature, the inputs will be read automatically from the custom aggregation rule as they will be labeled with "operation": RawFeature.
- aggregation: In our example, the syntax tree would be {"operation": Diff, "args": [{"operation": Ratio, "args":[{"operation": RawFeature, "args"["team_corners_infavor"]}, {"operation": RawFeature, "args"["team_corners_against"]}]}, {"operation": Ratio, "args":[{"operation": RawFeature, "args"["opponent_corners_infavor"]}, {"operation": RawFeature, "args"["opponent_corners_against"]}]}]}. When parsing the trees, the names of the input columns will be collected.

### Request budget and endpoint ownership

Let `A` be event occurrences processed in the discovered rounds, `M` the completed match rows subsequently exported, `R` the discovery calls, and `F` the lineup repair calls. With boolean switches `S` for shots, `H` for heatmaps, `L` for lineups, and `C` for commentary, the historical source's intended endpoint-navigation count is:

`Q_current = R + (2 + S + 2C)A + (2H + L)M + F`

For a clean completed season with unique events, `A = M`, the normal profile is `Q_current = R + 6M + F`. A 380-match, 38-round season therefore needs 2,318 navigations plus repairs. Browser auxiliary requests, failures, redirects and future retries require separate measurement and are not included in this formula.

| Component | Existing endpoint relative to `/api/v1` | Cold request cost | Planned treatment |
|---|---|---|---|
| Discovery | `/unique-tournament/{league}/season/{season}/events/round/{round}` | One per round request | Persist complete event objects; validate any replacement discovery strategy |
| Pregame positions | `/event/{id}/pregame-form` | One per match | Retain for equivalent historical position semantics |
| All match statistics | `/event/{id}/statistics` | One per match | Parse both teams and every reported period from the same response |
| Individual shots | `/event/{id}/shotmap` | One per match | Keep by default; team total xG is not an equivalent substitute |
| Team heatmaps | `/event/{id}/heatmap/{team_id}` | Two per match | Reuse both arrays in each response; no per-player heatmap loop |
| Lineups and reported absences | `/event/{id}/lineups` | One shared call per selected match | Both teams and candidate `missingPlayers` lists; no duplicate call for injuries |
| Commentary | `/event/{id}/comments` | One per match when enabled | Reuse discovery metadata instead of the current extra event lookup |
| Timing, match-time injury reports and goal sequences | `/event/{id}/incidents` | Up to one shared extra call per selected match | Pilot confirms bundled sequences and added-time announcements; exact duration remains unavailable |
| Event-detail enrichment | `/event/{id}` | Only when a needed field is absent from discovery | An explicit, budgeted fallback, not a default request for every match |
| Goal buildup actions | Bundled `footballPassingNetworkAction` inside `/event/{id}/incidents` | Zero beyond the shared incidents request | Observed in the pilot; preserve ordered actions and qualified recipient evidence |

The six-request figure above is the original profile before new enrichment. For a unique, eligible cold match, the shared lineup dependency is `include_lineups OR include_injuries`. The shared incidents dependency is the union of validated duration, requested match-time injury evidence, and any goal-discovery requirement not already satisfied. Count each shared request once. Let `B` be the measured goal-action fetch count and `D` any additional unmet discovery dependencies: goal enrichment adds `B + D`, not an assumed constant per match. If the provider serves one sequence per goal, `B` is the number of eligible uncached sequences attempted; failures and retries still count. Missing-player parsing adds zero calls when the lineup response is already obtained and contains the needed fields.

The first guaranteed improvements are eliminating needless lineup repairs and commentary metadata lookups, filtering irrelevant statuses early, and avoiding repeated work. Cache savings depend on what is already collected and how fresh it must be. Offline transformation of complete cached inputs should use zero calls. Repeated discovery of a still-active season can remain necessary even when no detail endpoints are due.

Do not claim that browser reuse, larger delays, async code, column selection, HTTP 304 responses, or a VPN reduces the number of required data requests. Do not replace pregame positions with the final table or a simplistic reconstruction; sanctions, tiebreaks, rescheduled games and competition stages can change the result.

### Phase 3: Implement pacing, response validation and bounded recovery

1. Separate `page_load_timeout_seconds`, `min_interval_seconds`, rolling minute/hour budgets, maximum attempts, and backoff settings. Start with concurrency one. The actual allowance is configurable; this review has not established a safe requests-per-hour threshold.
2. Record every outbound attempt before dispatch, including discovery, retries and optional enrichment. Enforce the same budget across components, seasons and restarted processes; prevent two local collector runs from silently doubling it with a shared ledger/lock.
3. Use a monotonic clock for waits, persisted UTC attempt times for restart accounting, and bounded backoff with jitter for transient failures. Honor `Retry-After` where available. A cooldown must survive restart.
4. Obtain response status/headers through the supported browser network interface and associate them with the intended request. Validate URL, content type, parseability and endpoint shape. A timeout must never cause the previous page's JSON to be attributed to the next match.
5. Classify success, valid empty content, confirmed unavailable coverage, not-yet-available content, rate limiting, access blocking, transient transport failure, and schema/parse failure. Do not identify a 404 by equality with one exact JSON string.
6. On 429, respect the advertised wait and apply a global cooldown. On 403 or a challenge/block page, checkpoint and pause the run; do not continue probing every match or automatically rotate routes. Malformed payloads retain diagnostic context without entering prepared data.
7. Use bounded retries only for retryable conditions. Do not repeatedly retry a confirmed missing historical endpoint within a run. A temporary failure must never overwrite a previously successful payload.
8. Capture lightweight request logs and totals without retaining cookies or authorization headers. Count API calls separately from browser auxiliary traffic so request estimates remain interpretable.

Completion evidence: fake-clock tests demonstrate spacing, hourly enforcement, persisted cooldowns, bounded retries, correct response association and clean cancellation.

| Quantity | Meaning | Availability rule |
|---|---|---|
| Nominal period duration | Scheduled regulation/extra-time length for that competition | Store separately when known; it is not a measured duration |
| Announced added time | Referee's announced allowance at a period end | Retain as an announcement/minimum, not exact elapsed time |
| Half elapsed duration | Actual period start to whistle, including stoppages within that half | Populate only with validated timing evidence and stated precision |
| Match playing-period duration | Sum of elapsed played periods, excluding breaks and shootout | Require a complete compatible set of period measurements |
| Wall-clock elapsed duration | Actual kickoff to final whistle, including halftime and other breaks | Require actual boundary timestamps; scheduled kickoff alone is insufficient |
| Ball-in-play time | Time while the ball is in play | Leave unavailable unless a distinct validated provider metric exists |

Chrome inspection of [Vissel Kobe–Kashima Antlers](https://www.sofascore.com/football/match/vissel-kobe-kashima-antlers/JmbsWmb#id:16348595) showed added-time announcements of one and seven minutes, and HT/FT markers, but no exact whistle timestamp in the inspected text. [IFAB Law 7](https://www.theifab.com/laws/latest/the-duration-of-the-match/) establishes that the announcement is a minimum and can be increased. Therefore adding the announced values to 90 minutes cannot establish exact match duration.

Direct API navigation returned `ERR_BLOCKED_BY_CLIENT`, and the web tool also could not open that API URL. API field availability and semantics were not verified live. The wrapper author's [match module source](https://tommhe14.github.io/sofascore-wrapper/_modules/sofascore_wrapper/match.html) supplies an implementation lead for structured incidents and examples of time fields. Its FT example has `time=90`, `timeSeconds=5400` and `addedTime=999`; these examples are not official Sofascore guarantees. Treat 999 as a possible sentinel to reject, not as minutes of real play. Validate the current payload before deriving durations.

#### Implementation sequence

1. Retain existing discovery timing metadata at no additional request cost. Inspect candidate fields such as `time.injuryTime1` through `injuryTime4`, `startTimestamp`, `time.currentPeriodStartTimestamp`, status and change timestamps. Field names are investigation targets, not a promised current schema.
2. Add modes `duration_mode=metadata`, `incidents`, and `off`. `metadata` is the initial default and makes no extra timing request. `incidents` adds one shared structured-incident fetch per eligible uncached event after its schema has been validated; keep comments disabled.
3. In a small paced investigation, compare old and recent matches, standard full time, extra time/shootout, a long-stoppage match, and low-coverage or abandoned cases. Inspect raw incident period markers, `time`, `addedTime`, `timeSeconds`, `periodTimeSeconds` or other supplied clock fields, and actual event timestamps if present.
4. Establish whether each clock is a regulation-minute label, period-local elapsed clock, cumulative match clock excluding earlier stoppage time, or wall-clock timestamp. Do not infer meaning from the field name alone. Confirm HT and FT boundaries against observable match evidence.
5. Explicitly reject sentinel values, impossible ranges, missing period starts and inconsistent time bases. Do not use last update time as final-whistle time, or goalkeeper `minutesPlayed`, last shot time or last substitution time as full duration.
6. When second-half clock labels reset to 45, interpret that reset correctly: a valid second-half end at 90+7 describes 52 minutes of that half at minute precision, not a value from which the first half's 45+added-time endpoint should be subtracted. Preserve the uncertainty from rounding.
7. Derive a period duration from validated start/end timestamps, or from a validated recorded elapsed period clock. Store evidence method, units and precision alongside the value. Sum only compatible complete period measurements. A partial sum must never be named total match duration.
8. If only announcements exist, store them and leave measured duration null. Optionally expose the sum of nominal periods plus announced additions as `announced_minimum_play_minutes` for completed standard matches, with that exact meaning. Keep incomplete/abandoned cases out of that calculation.
9. If a valid last timed incident is useful, expose a separate period lower bound with its evidence. It must not fill the exact-duration column. Do not infer ball-in-play time by subtracting a few known stoppages.
10. Represent extra time as periods three/four, and keep halftime/extra-time intervals and penalty-shootout timing separate. For competition-specific shorter matches, use verified period lengths instead of hard-coded 45/90.
11. Allow a targeted event-detail fallback only if it supplies a necessary missing field and its extra request is included in the plan. If incidents contain no useful improvement over metadata, stop scheduling them by default and retain `metadata` mode.

Proposed normalized period fields: `event_id`, `period`, `nominal_seconds`, `announced_added_minutes`, `elapsed_seconds`, `duration_quality`, `precision_seconds`, `source_endpoint`, `source_fields`, `fetched_at_utc`. Quality distinguishes exact boundary evidence, recorded approximate clock, announcement only, lower bound only and unavailable. Match-level fields include regulation playing-period seconds, extra-time seconds, total playing-period seconds, wall-clock seconds, completeness and derivation method. Unknown values remain null.

Completion evidence: a timing coverage report by league/era and validated examples for every supported derivation. If exact duration cannot be recovered reliably, the completed feature reports that limitation and retains the evidence; it does not fabricate values or launch a high-frequency live recorder as a workaround.

#### Prepared storage design and migration

The current CSVs are readable, but the nested objects and duplicated derived files make them a poor long-term primary layout. The match/lineup folder contains 2,347,254,093 bytes of CSV data and the promotion-enriched folder another 1,803,793,685 bytes. An inspected Premier League 2024–25 match file has 302 columns; its enriched counterpart has the same columns plus four promotion/demotion flags. Its first home heatmap cell is 19,615 characters. These are measurements of the current layout, not a measured Parquet compression ratio.

1. Define a versioned Arrow schema with nullable integer IDs, explicit numeric/boolean columns, UTC timestamps and source-status fields. Store identifiers in columns, not an implicit pandas index. Keep unknown values null and retain a separate distinction between valid empty components and unavailable components.
2. Use the following table grains. Every child record links to its source component and retains source order where meaningful. A provider ID is preferred; where absent, a local key combines the parent ID, source response identity and record ordinal, without presenting that local key as a provider ID.

   | Table | Grain and key |
   |---|---|
   | Matches | One current canonical row per provider/event ID; competition, season and stage remain explicit |
   | Statistics | Event, team, period, statistic key; retain raw display value alongside numeric value/unit where supplied |
   | Shots | One source shot per event, preserving shot ID or local ordinal and all available timing/coordinates |
   | Heatmap points | Event, team, point kind (player/goalkeeper), source point ordinal, coordinates and supplied weight |
   | Lineups | Event, team, player and observation snapshot; formation belongs in a team snapshot, not duplicated per player |
   | Player match statistics | Event, team, player, observation snapshot and statistic key |
   | Timing, availability and goal actions | Their previously defined period, snapshot and ordered-action grains |
   | Team-season membership and flags | Provider, competition, season and team ID; movement status and evidence |

3. Start with files grouped by competition and season for substantial tables. Avoid one tiny Parquet file per match. Keep small dimension tables together and keep cached response files independent from analytical partitioning. Benchmark the proposed point-table layout against typed list/struct heatmap columns on a representative season before freezing that specific layout; neither candidate stores Python-literal text.
4. Benchmark Zstandard and Snappy compression, full-season reads, projected match-statistic reads, heatmap/lineup reads, and peak memory on the same records. Compare against the existing CSV loader including nested parsing. Parquet supports compression and column projection as documented by [Apache Arrow](https://arrow.apache.org/docs/python/parquet.html); report actual measurements rather than promising a reduction factor.
5. Import existing CSVs locally with safe mixed JSON/Python-literal parsing, record file hashes and `legacy_prepared` provenance, and preserve known discarded-field limitations. Do not invent a raw API archive from these prepared records. Migration itself requires no API calls.
6. Publish into a separate versioned directory. Validate unique keys, referential integrity, row counts at each table grain, point/action order, numeric precision, missingness and reconstruction of the legacy view. Compare promotion flags separately from unchanged match facts.
7. Update the loader to request only required tables and join by IDs. Retain compatibility CSV output until the relevant consumers pass parity checks. An independent Parquet file write is not a transaction across a whole dataset: publish the output manifest only after all tables validate, then switch the active-version pointer atomically.
8. Keep original CSVs and enriched files during this refactor. Removing them is a separate storage-cleanup decision. Preserve the capability to regenerate the compatibility view from canonical tables and team-season flags.

Completion evidence: a reproducible size/time/memory benchmark, a schema report, faithful round-trip of supported legacy content and validated consumer loading. Format conversion cannot repair xG defaults or recover discarded player, timing or goal-action fields.

### Implementation order and decision boundaries

Implement phases 1–4 first to establish contracts, real pacing, reliable responses and resumability. Follow with discovery and component parsers in phases 5–6, then timing validation in phase 7 and export/consumer work in phase 8. Several proposals depend on evidence rather than preference: an alternative discovery endpoint must be cheaper and complete; exact duration must have validated boundary/clock semantics; historical xG recovery needs trustworthy source payloads; injury reports need verified source meanings; and goal actions need a validated structured payload.
